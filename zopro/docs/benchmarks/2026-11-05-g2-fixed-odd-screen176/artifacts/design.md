# Fixed-window odd-digit work screen

Hypothesis: fixed-window odd digits may change bucket occupancy and reduction cost without the 127 bit positions of the rejected bitwise NAF recipe. Test one fixed width-12 representation with eleven radix-4096 windows and 2,048 positive odd-magnitude buckets per window. There is no width sweep, native performance claim, or inherited positive result.

For a nonzero magnitude m < 2^126, choose skew = 1 when m is even and 0 otherwise. Encode m+skew with odd signed digits of absolute value < 4096. At each step choose the low residue or that residue minus 4096 so the next remaining value is odd. Then make one ascending pass collapsing a ±1 digit into its opposite-signed predecessor when that preserves the range. Include the final window in this pass. Zero maps to all-zero digits and zero skew. Signed components negate both digits and correction. Verify the exact signed radix-Horner identity after subtracting the correction; verify every nonzero digit is odd and in range. This is an independently written fixed recipe, inspired by the audited libsecp256k1 representation; it is not an imported implementation or a port of its MSM.

Primary source audited at bitcoin-core/secp256k1 commit cc0e03ffd4ddfce3663dc807a10cc4e3d0132d79, src/ecmult_impl.h. Its fixed recoder and bucket method require skew correction, and differ from conventional bitwise NAF. Our final-window collapse and separate correction tree are explicit recipe choices.

Count main digit arrivals, first writes, part merges, maximum used bucket slot, and an explicit dense weighted fold: 2*(last_used_slot-1) generic additions per active position. For odd weights, an efficient shifted fold reuses its running total and also needs one doubling for each active position with more than one used slot; report these doublings separately rather than treating them as free. The control's ordinary radix fold uses the same declared generic-addition model, with no odd-weight doubling.

Charge all skew corrections through a separate signed point-sum tree. For s correction leaves, a binary tree takes s-1 generic joins and final combination takes one, giving s generic additions when s > 0. These are hypothetical generic joins, not complete curve execution costs. This avoids claiming that a highly concentrated bucket-zero correction stream is harmless to the existing queue.
