# Zopro and Aeglos: fresh c7a.24xlarge and Ryzen comparison

Measured on 23 October 2026 using retained Zopro f5c720 and Aeglos 0290613. The AWS advantage for Aeglos reproduces with the current retained implementation. Zopro wins the fresh local comparison at each prover's best tested worker count; Aeglos wins the AWS comparison at each prover's best tested count. This is evidence about these two hosts and tested configurations, not every CPU.

The crosshost control uses exactly the same image and executable hashes on both hosts, including the Zopro build targeting znver4. The separate all-nine native Ryzen run is linked below. No experimental optimization was promoted by this comparison.

## Why the machines disagree

The same-image control reproduces the local advantage: 1x2 is 11.093 ms for Zopro versus 12.718 ms for Aeglos at 32 workers; 54→1 is 295.820 ms for Zopro at 32 versus 992.750 ms for Aeglos at its better local count of 16. These are close to the independently built native-local results. A stale implementation or different compiler target does not account for the reversal.

Aeglos scales substantially across the server’s additional physical cores. Its AWS 54→1 latency falls from 612.443 ms at 16 workers to 174.225 ms at 96. On Ryzen, increasing workers from 16 to 32 adds SMT threads and leaves its latency near one second. Its local 54→1 profile spends about 90% of elapsed proving time in MSM. Aeglos's source uses shifted base tables and gathered point accesses; its local profiles spend approximately 40–42% of sampled user cycles in pair loading. The larger server cache and memory system are plausible contributors, but this experiment does not isolate their individual effects or measure DRAM bandwidth. The CPU's physical-core count alone also does not explain the whole difference: Aeglos already performs better on AWS at 16 workers.

Zopro has two distinct scaling problems in these measurements:

1. **Small proofs accumulate scheduling overhead.** On AWS, 1x2 improves up to 32 workers, then regresses. Crossbeam epoch operations account for 50.21% of sampled user cycles at 96 workers, versus 10.54% at AWS 32 and 8.18% at local 32. Its voluntary context switches rise from about 586 to 1,644 per proof on AWS 32→96. These samples establish substantial overhead, not a claim that removing that percentage would remove the same percentage of wall time. Aeglos's pool also spends cycles waiting, so zero-wait scheduling is not the comparison standard.
2. **Large proofs encounter severe page-table lock contention.** The unprofiled 54→1 runs show the following process CPU totals per proof. CPU time is summed across threads.

| AWS workers | Zopro user CPU ms | Zopro kernel CPU ms | Zopro minor faults | Aeglos kernel CPU ms | Aeglos minor faults |
|---:|---:|---:|---:|---:|---:|
| 32 | 5,831 | 2,641 | 160,007 | 25 | 2,719 |
| 64 | 8,159 | 9,072 | 244,645 | 41 | 2,697 |
| 96 | 11,161 | 16,604 | 296,715 | 109 | 3,686 |

A separate kernel-only profile at 96 workers attributes 92.16% of sampled kernel cycles to `__pv_queued_spin_lock_slowpath`. A follow-up call-chain profile puts approximately 91% under `do_anonymous_page → pte_offset_map_lock → _raw_spin_lock`. This identifies contention during anonymous-page faults. It is more specific than attributing the entire regression to the Rust scheduler. Both kernel profiles and the follow-up call-chain recording report zero lost samples. The raw call chains are in [the kernel diagnostic](kernel-callchain/remote-results/output/kernel-callchain/kernel-zopro-merge-54x1-w96-flat.txt).

## Targeted page-touch diagnostic

After identifying the page-table contention, a separate, predeclared diagnostic compared the unchanged executable, an inactive allocation hook, and the active hook. The active hook touches one byte per page for allocations of at least 1 MiB before the allocation returns to parallel code. It introduces no additional allocation or retained buffer. Reallocation preserves existing contents. Local boundary checks covered malloc/calloc/realloc contents and aligned allocations before the experiment.

This is a Linux/glibc interposition experiment, not a portable production implementation. It affects allocation initialization, including inside the measured proof loop; that work is included in the timings. All three cases used 96 workers, three reversing fresh-process repetitions, three excluded priming requests and 17 measured requests per process.

| Case | Median ms | User CPU ms/proof | Kernel CPU ms/proof | Minor faults/proof | Max whole-process RSS MiB |
|---|---:|---:|---:|---:|---:|
| Unchanged executable | 421.539 | 11,136 | 16,468 | 294,842 | 3,105.6 |
| Hook inactive | 422.029 | 11,112 | 16,549 | 296,754 | 2,681.5 |
| Touch pages before return | 285.807 | 11,235 | 513 | 77,408 | 2,791.1 |

The active hook wins all three paired repetitions against both controls, reducing paired median latency by 32.2% versus the unchanged executable and 31.9% versus the inactive hook. It passes the diagnostic's necessary 10% improvement and ≤1.2× native peak-RSS gate. Peak RSS varies with allocation placement; the active run is approximately 4.1% above the inactive hook, so the lower maximum versus the unchanged control is not evidence of a memory-saving technique.

This is **about 8.0% lower latency than the best unchanged configuration, 310.649 ms at 32 workers**, not a 32% improvement over that best configuration. It still takes about 1.64× Aeglos's 174.225 ms. CPU cost per proof remains higher than unchanged Zopro at 32 workers, so this does not establish better concurrent throughput. The causal result supports improving initialization and reuse of budgeted proof workspace. It does not qualify the hook for production, mobile devices, larger circuits or memory pressure.

## Next implementation targets

First locate the allocations and parallel writes responsible for the page faults, then implement bounded workspace reuse or controlled initialization at those ownership boundaries. Preserve the existing memory admission and release policy, and measure peak memory as well as latency. Independently address excessive work stealing and synchronization for small proofs. The small-proof result needs its own scheduling fix; the 54→1 page-touch result does not establish an improvement for 1x2. Test a concrete implementation on both hosts, across all circuits and under memory pressure before adoption.

The main latency run had no OOM or memory-limit events and accumulated only 0.255 seconds of throttled CPU time across all 216 processes. Those mechanisms do not explain its large scaling regression. All conclusions remain specific to the measured hosts, software and warm single-proof workload.

## Validation and artifacts

AWS: 216 latency processes plus 16 profile processes; 5,864 measured and 696 priming requests, all internally verified. All 232 distinct exported measured proofs passed Gnark on AWS and were independently reverified locally after retrieval. The exact-image local control adds 58 processes including all-nine preflight, 2,450 measured and 174 priming requests, and 58 distinct Gnark-verified measured proofs. Total: 9,184 requests and 290 distinct exported proofs. The separate native all-nine report adds 2,328 requests and 108 distinct proofs; these are not counted again here.

Proof hashes, fixed public inputs, source hashes and exact executable hashes were checked. Raw perf records were parsed for lost-event records. Phase-specific CPU throttling and memory-event snapshots are in `crosshost-analysis.json`. The temporary instance, its tagged EBS volume and the new benchmark ECR tag were removed after retrieval and verification; lifecycle receipts are included. No production source change was made.

- [Complete analysis](crosshost-analysis.json): all worker counts, process medians, stages, CPU usage, counters, profiles and audit results.
- [AWS comparison](results.json), [AWS raw results](aws-results/output/latency/rows.json), [AWS profiles](aws-results/output/profile/rows.json).
- [Exact-image local results](local-results/local/rows.json), [local profiles](local-results/local-profile/rows.json).
- `binaries.tar.gz`, `source-snapshots.tar.gz`, driver sources, image manifests, fixtures, scripts, proof/public files and `SHA256SUMS` preserve reproduction evidence. Key contents are identified by the key lock and are not duplicated in this report.

Initial preparation failures are preserved: a manifest dictionary/string assertion before building or timing, and local output-directory permissions before any preflight proof. Both were corrected without changing the measured prover sources or binaries. These failures are not counted as measured runs.

After the main protocol, three supplementary diagnostics add 240 requests and 12 distinct independently verified measured proofs: two kernel-only profiles, one kernel call-chain profile and nine page-touch comparison processes. Including these, this report preserves 9,424 requests and 302 distinct exported proofs; 244 actual AWS samples were independently reverified locally. Supplementary results are kept separate from the main latency table. An AWS SSM rate-limit error interrupted result retrieval; completed chunks and command handles were retained, retrieval resumed with fewer concurrent requests and bounded throttling retries, and archive SHA-256 checks passed. No latency run was repeated for this transport failure.

This measures warm single-proof latency, not concurrent throughput, cold startup, phone execution, TEE operation, or a 211-million-constraint circuit. Zopro's ≤9 ms target and the original all-eight 10× M5 CPU target remain unmet.
