# Remaining native design costs

The count passes a necessary generic-add screen only. On primary it removes60,973 modeled generic additions while adding53,020 affine phi maps (106,040 Fq multiplications), plus19 separately reported projective axis-result phi maps. Dense Horner doublings increase120→126. Scalar/ring recoding, signed coordinate routing, input/axis point conversion, inversion batches, queue exceptions and weighted-tree projective operations are unpriced. No measured speedup or native eligibility follows automatically.

The three planes contain8,193 G2 affine points per original point-range part:1,048,704 coordinate bytes versus262,144 for2,048 original buckets. If all19×2 dense part arrays coexist, coordinate payload alone is39,850,752bytes (38.005MiB), versus5,767,168bytes (5.5MiB) for all11×2 original arrays. These are hypothetical dense-array payloads, not actual peak liveness, allocations, RSS or minimum RAM. They exclude metadata, exceptional projective points, batch queues, prefix/weighted/axis scratch, live key/witness/solver/FFT memory and allocator/stack effects. A scheduler may retain fewer part arrays, but that requires a concrete ownership/lifetime design and measurement, not a smaller number assumed here.

An optional compact implementation could represent each of16,384 residue entries with a signed i16 plane/bucket code plus two i8 coordinate corrections,64KiB total; representatives need5,462 coordinate bytes. Norm<=5,419 implies each representative coordinate's absolute value<=85, so i8 fits. These formats are proposals only: the diagnostic Table intentionally has larger Rust structures. New digits would occupy38bytes per scalar (1,143,382bytes on30,089 raw primary rows), in addition to any simultaneously retained original32-byte split-scalar storage. Do not call either map or digit estimate a native memory guarantee.

Next stage must first model the actual indexed top and both coordinate weighted trees, including generic affine versus projective operations, zero groups, batch/tail geometry and phi work. Then define checked admission for every concurrently live new vector and preserve the original borrowed-input fallback, complete exceptional handling, original key/image representation and existing pool. A giant point lookup table, retained duplicate key/plan or arbitrary fixed RAM cap is not part of this recipe. The larger planes are a material risk; a count win alone cannot justify the memory increase.
